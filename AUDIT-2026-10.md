## 🟠 1. Le Win Rate est journalier, la documentation dit « par période »

`metrics.py` calcule toutes les statistiques gain/perte sur `returns = equity_curve.pct_change()`,
c'est-à-dire sur les rendements **journaliers** (`metrics.py:59`), et prend la valeur absolue
des pertes :

```python
winning_returns = returns[returns > 0]          # metrics.py:103
win_rate   = len(winning_returns) / len(returns)
avg_loss   = abs(losing_returns.mean())
max_loss   = abs(returns.min())
```

Or l'interface annonce autre chose, à deux endroits :

- `ComparisonTable.tsx:82` — « Percentage of **rebalancing periods** with positive returns. »
- `DocumentationPage.tsx:935` — « Win Rate : % de **périodes de rebalancement** positives »

**Preuve.** Sur l'univers par défaut (2006-04-28 → 2026-10-20), MVO affiche 55,9 %. Il y a
4 898 jours et 78 rebalancements. Un portefeuille à 9,85 % de CAGR a environ deux trimestres
gagnants sur trois, pas 55,9 % ; 55,9 % est en revanche exactement la proportion de **jours**
positifs attendue. La valeur est bonne, c'est l'étiquette qui est fausse.

**Correctif (petit).** Renommer en « % de jours positifs » dans l'infobulle et la doc.
**Correctif (meilleur).** Calculer réellement le win rate par période de détention : c'est
l'information que promet le tableau, et elle est plus parlante que la proportion de jours
verts. Les séries nécessaires (`monthly_returns`, bornes de rebalancement) existent déjà
côté serveur.

> Même famille : `avg_win`, `avg_loss`, `max_gain`, `max_loss` sont journaliers et les pertes
> sont des magnitudes. Ils ne sont pas affichés dans le tableau, mais ils sortent dans
> l'export — qui les étiquette depuis `exportReport.ts` comme « jour » et « magnitude ».

## 🟠 2. Quatre CVE « high », dont deux pour un paquet inutilisé

`npm audit --omit=dev` :

| Gravité | Paquet | Versions touchées | Statut ici |
|---|---|---|---|
| high | `axios` | 1.0.0 – 1.19.0 | **1.13.2 installée**, utilisée par tous les appels API |
| high | `form-data` | 4.0.0 – 4.0.5 | transitive via axios |
| moderate | `follow-redirects` | ≤ 1.15.11 | transitive via axios |
| high | `react-router` | 6.0.0 – 7.18.1 | transitive |
| high | `react-router-dom` | 7.0.0-pre.0 – 7.14.1 | **7.13.0 installée** |
| moderate | `yaml` | 1.0.0 – 1.10.2 | dev seulement (cosmiconfig) |

`react-router-dom` n'apparaît **qu'une seule fois** dans tout le code :

```tsx

import { BrowserRouter } from 'react-router-dom'
```

Aucun `Route`, `Link`, `useNavigate` ni `useParams` nulle part — l'application navigue par
onglets MUI. Le routeur enveloppe l'arbre et ne fait rien.

**Correctif.** Supprimer la dépendance et le `<BrowserRouter>` (deux CVE « high » et ~20 Ko
en moins), puis `npm i axios@^1.20` (les deux CVE transitives disparaissent avec).

> **Fait.** `npm audit --omit=dev` ne trouve plus **aucune** vulnérabilité.
>
> En revanche, l'audit complet (dev compris) en montre quatre autres, toutes dans la chaîne
> **vitest** : `tinypool` (**critical**, prototype pollution → RCE via les options de worker),
> `@vitest/mocker` et `vitest` (moderate, path traversal). Elles ne touchent que la machine
> qui lance les tests, pas le site, mais le correctif est un **majeur** (`vitest` 3.2 → 5.0)
> qui n'a pas sa place dans une PR de correctifs ponctuels. À traiter à part.

## 🟠 3. Deux taux sans risque dans le même run

`fetch_risk_free_rate_history` plafonne par le bas l'historique FRED :

```python
# data_provider.py:348
if start_date is None:
    start_date = "2010-01-01"
```

et `run_comparison_job` l'appelle **avant** de connaître les prix, avec `request.start_date`
(`routes.py:275`) — qui vaut `None` dès que la case « Use full history » est cochée, c'est-à-dire
par défaut. Conséquences sur un run qui commence en 2006 (cas de l'univers par défaut, limité
par SLV au 2006-04-28) :

- dans le moteur, `risk_free_rate.asof(date)` renvoie NaN avant 2010 → repli **4 % constant**
  pour 2006-2009 (`backtester.py:280`, `backtester.py:410`) ;
- pour les métriques, `rf_metrics` est la moyenne de la série **2010+ uniquement**
  (`routes.py:293-296`) — le run affiche « Risk-Free: 1,41 % ».

Donc la rémunération du cash dans la courbe et le taux qui sert à calculer tous les Sharpe
ne décrivent pas la même chose, et aucun des deux ne couvre 2006-2009 correctement (les taux
y sont passés de ~5 % à ~0 %).

**Correctif.** Récupérer l'historique FRED **après** `fetch_price_data`, en partant de
`prices.index[0]`. Une ligne à déplacer et un paramètre à passer ; le reste du calcul ne
change pas.

## 🟡 4. La date de l'allocation courante est « aujourd'hui »

```python
# routes.py:220
current_alloc = CurrentAllocation(
    date=datetime.now().strftime("%Y-%m-%d"),
```

Ce n'est pas la date de la décision : c'est l'heure du serveur. Le dashboard n'utilise pas ce
champ (il affiche `results.data_end_date`, correct), mais l'API le publie et l'export JSON le
transporte. La bonne valeur est `allocation_history[-1]["date"]`.

## 🟡 5. Le benchmark est fusionné par index dans le graphe principal

```tsx
// ComparisonChart.tsx:117-123
const rawData = methods[0].equity_curve.map((point, index) => ({
    date: point.date,
    benchmark: benchmarkCurve[index]?.value || 1,
    ...
```

Entre stratégies, l'alignement par index est exact (même calendrier, même longueur). Pour le
benchmark c'est faux d'une séance : les stratégies sont valorisées à partir de T+1, un
benchmark custom à partir de T, et sa courbe a un point de plus avant sous-échantillonnage.
Invisible à l'œil sur 500 points, mais l'infobulle associe la valeur du benchmark à la date
de la stratégie. Une `Map` date → valeur règle le problème (c'est ce que fait déjà
`exportReport.ts`, avec une tolérance d'une semaine).

faux : contre lui-même, le beta vaut 1,00 et l'alpha 0. Soit on passe la série à elle-même,
soit on affiche « — » sur cette cellule.

## 🟢 Optimisation et exploitation

**11. CORS ouvert en production.** Vérifié :

```
$ curl -D - -H "Origin: https://evil.example" https://bestallocation.onrender.com/api/health
access-control-allow-origin: *
```

`ALLOWED_ORIGINS` n'est pas défini sur Render. L'API n'a pas d'authentification et sert son
propre frontend : la fixer à `https://bestallocation.onrender.com` ne coûte rien et évite
qu'une page tierce fasse tourner des backtests sur ton quota Tiingo depuis le navigateur de
ses visiteurs.

**À vérifier dans la même foulée : `TRUST_PROXY`.** Sans elle, le rate limiter prend l'IP du
proxy Render comme clé — *tous* les visiteurs partagent le même seau de 5 requêtes/minute.
Render réécrit `X-Forwarded-For`, donc `TRUST_PROXY=1` est le bon réglage ici (c'est
exactement le cas documenté dans le README).

**12. Un seul chunk de 1,2 Mo.** Le build découpe bien les graphes (3 à 13 Ko chacun), mais
React, MUI et Recharts sont tous dans `index-*.js` — 1,2 Mo non compressés. Render sert en
Brotli (vérifié : `content-encoding: br`), donc le transfert est raisonnable, mais le parsing
reste sur le fil critique. Un `build.rollupOptions.output.manualChunks` séparant
`react`/`mui`/`recharts` améliore le premier rendu et rend le cache navigateur utile entre
deux déploiements : aujourd'hui, changer une ligne invalide les 1,2 Mo.

**13. Pas de veille sur les dépendances.** Dependabot (ou `npm audit` + `pip-audit` dans la
CI) aurait signalé les quatre CVE du point 2 à leur publication. Pour un projet déployé en
public, c'est le meilleur rapport effort/risque de cette liste.

**14-15. Hygiène.** `lastRebalancingWindow` est passé de `App` à `Dashboard` sans jamais être
lu (et `runParams` fait mieux depuis la PR #20). `JobManager.cleanup_expired_jobs`
(`jobs.py:58`) ne purge que les jobs `completed`/`failed` : un job interrompu reste en mémoire
indéfiniment. Mesuré : un résultat pèse 334 Ko (dont 316 Ko pour les trois stratégies), donc
rien d'urgent — mais la condition mérite d'inclure un âge maximal absolu.

## 🟢 Ce qui est réellement solide (vérifié, pas survolé)

- **Le moteur walk-forward.** Relu ligne à ligne : optimisation sur les Close jusqu'à T,
  exécution à l'Open T+1, blocs de détention contigus sans trou ni doublon
  (`backtester.py:396-398`), arrêt propre quand il n'existe pas de T+1 (`backtester.py:258`),
  coûts facturés par côté sur la valeur tradée, y compris le déploiement initial — pour les
  stratégies **et** pour le benchmark équipondéré.
- **Les statistiques pleine résolution.** Stress tests, Sharpe glissant, rendements mensuels
  et annuels sont tous calculés avant le sous-échantillonnage, et les composants frontend
  portent le commentaire qui explique pourquoi il ne faut pas les reconstruire côté client.
  J'ai cherché une régression de cette famille : il n'y en a pas.
- **La suite de significativité.** Bootstrap par blocs circulaires avec les **mêmes** indices
  pour les deux séries, graine fixe, PBO par CSCV vectorisé via statistiques suffisantes,
  DSR avec correction skew/kurtosis et son `tail_adjustment` reporté, rank-IC publié avec son
  plafond de détectabilité. C'est du travail sérieux, et les tests vérifient les deux sens
  (détecter un effet réel *et* refuser d'en détecter un absent).
- **La sécurité de base.** `resolve_spa_file` résout puis vérifie l'inclusion (le bon ordre),
  le conteneur tourne en non-root, `.dockerignore` existe, `.env` n'est ni suivi ni présent
  dans l'historique git, la clé FRED est masquée dans les logs d'erreur, et tous les tickers
  — benchmark compris — passent par `normalize_ticker`.
- **Le déterminisme.** Graine fixe pour le bootstrap et pour le nuage Monte-Carlo, sur un
  `Generator` local et non sur l'état global NumPy partagé par trois threads.
- **L'outillage.** CI bloquante sur quatre étapes, cache joblib borné à 500 Mo, throttle
  Tiingo partagé entre threads, `requirements.txt` en intervalles avec plafond majeur.
- **L'export de run (PR #20)** est en ligne : le bundle déployé contient bien le bouton.
