## 🔴 1. Traversée de répertoire — n'importe quel fichier du serveur est lisible

**Fichier :** [`backend/main.py:100-108`](backend/main.py#L100)

```python
@app.get("/{full_path:path}")
async def serve_spa(full_path: str):
    file_path = FRONTEND_DIR / full_path      # full_path vient du client, tel quel
    if file_path.exists() and file_path.is_file():
        return FileResponse(file_path)        # ← sert n'importe quoi
```

`{full_path:path}` capture les `/` **et** les `..`. Ni Starlette ni uvicorn ne normalisent
`scope["path"]` : `Path("frontend/dist") / "../../backend/.env"` se résout hors de
`frontend/dist`, `exists()` répond `True`, et `FileResponse` sert le fichier.

**Preuve (exécutée pendant cet audit, sonde ASGI brute, un faux `.env` déposé pour l'occasion) :**

```
/../../backend/.env.audit-probe   -> 200  len=41    LEAK=True
    b'TIINGO_API_KEY=SUPER_SECRET_PROBE_VALUE'
/../../backend/main.py            -> 200  len=4387  LEAK=True
```

**Pourquoi ce n'est pas théorique :** les navigateurs normalisent `..` avant d'envoyer, mais
`curl --path-as-is`, un script Python ou une socket brute ne le font pas. Et uvicorn
`unquote()` le chemin, donc `%2e%2e%2f` passe aussi. Dans l'image Docker, `FRONTEND_DIR`
vaut `/app/frontend/dist`, donc `/../../../etc/passwd` remonte à la racine — et le conteneur
tourne **en root** (aucune directive `USER` dans le `Dockerfile`).

**Ce qui fuit concrètement :** `TIINGO_API_KEY`, `FRED_API_KEY`, tout le code source, et sur
Render le contenu de `/proc/self/environ`.

**Correctif (3 lignes) :** résoudre puis vérifier le confinement avant de servir.

```python
@app.get("/{full_path:path}")
async def serve_spa(full_path: str):
    root = FRONTEND_DIR.resolve()
    candidate = (root / full_path).resolve()
    if candidate.is_file() and candidate.is_relative_to(root):   # Python 3.9+
        return FileResponse(candidate)
    return FileResponse(root / "index.html")
```

Un test de non-régression (`test_spa_rejects_traversal`) mérite d'accompagner le correctif.

## 🟠 2. `downsample_curve` jette la fin de toutes les courbes

**Fichier :** [`backend/app/api/routes.py:55-61`](backend/app/api/routes.py#L55)

```python
step = len(curve_data) / max_points
return [curve_data[int(i * step)] for i in range(max_points)]
```

Le dernier indice généré est `int(499 × step)`, jamais `len-1`. Sur 4 814 points, `step =
9,628` → le dernier point retenu est l'indice 4 805 : **les 9 derniers jours sont coupés**.

**Mesuré (HRP, univers par défaut) :**

```
courbe complète  — dernier point : 2026-06-18   valeur 4,425620
courbe affichée  — dernier point : 2026-06-05   valeur 4,326806
Total Return : tableau = 342,27 %   |   extrémité du graphe = 332,40 %   (écart 9,87 pts)
```

Le tableau « Performance Comparison » et la courbe d'equity, côte à côte sur l'onglet
Overview, ne racontent pas la même histoire. Ça touche aussi `drawdown_curve` et
`rolling_sharpe`, qui passent par la même fonction.

**Correctif :** garantir le dernier point.

```python
idx = sorted({int(i * step) for i in range(max_points)} | {len(curve_data) - 1})
return [curve_data[i] for i in idx]
```

## 🟠 5. Le benchmark affiche 0,00 % de coûts de transaction — alors qu'il en paie 1,06 %

**Fichiers :** [`routes.py:364-368`](backend/app/api/routes.py#L364) et
[`backtester.py:513-594`](backend/backtester.py#L513)

`get_equal_weight_benchmark()` facture bien les coûts (déploiement initial + chaque
rebalancement, comme le promet le README) — mais elle ne **retourne** que le turnover, pas le
montant. `routes.py` passe donc `total_costs=0` et `num_rebalances=0` pour la colonne
benchmark.

**Mesuré :**

```
somme nominale des coûts facturés : 1,06 % du capital initial, affichée 0,00 %
   (HRP, calculé de la même façon : 2,22 %)
```

> **Correction (post-vérification).** La première version de ce rapport annonçait 2,95 % et en
> concluait que le benchmark était « la ligne la plus chère du tableau ». Les deux affirmations
> étaient fausses. 2,95 % est l'écart de *valeur terminale* entre la courbe avec et sans coûts,
> c'est-à-dire les coûts **capitalisés** sur 19 ans — ce n'est pas la grandeur qu'affiche le
> tableau. La colonne « Transaction Costs » montre la somme nominale, et sur cette base le
> benchmark coûte **1,06 %** contre 2,22 % pour HRP : le 1/N est bien le moins cher, comme on
> l'attend d'une stratégie à faible turnover. Le défaut reste entier (une ligne à 1,06 %
> affichée à 0,00 %), seule ma comparaison était à l'envers.

Les *rendements* sont justes — les coûts sont bien dans la courbe. C'est la ligne
« Transaction Costs » du tableau qui affiche zéro.

**Correctif :** faire retourner le coût cumulé par `get_equal_weight_benchmark` (une variable
`total_cost` accumulée dans la boucle) et le passer à `calculate_metrics`. Pour un benchmark
custom (SPY buy-and-hold), 0 reste correct — il est affiché brut par convention.

## 🟠 6. `benchmark_ticker` échappe à la validation des tickers

**Fichiers :** [`schemas.py:185`](backend/app/core/schemas.py#L185),
[`data_provider.py:178`](backend/data_provider.py#L178)

`tickers` passe par un `field_validator` strict (`[A-Z0-9.\-]{1,12}`, anti-injection, ajouté
en juillet). `benchmark_ticker` n'a **aucune validation** et finit directement dans une URL :

```python
endpoint = f"/tiingo/daily/{ticker}/prices"   # ticker = benchmark_ticker.strip().upper()
```

`requests` ne normalise pas les `..` dans le chemin, donc un `benchmark_ticker` du type
`../../ACCOUNT/API/TOKEN` atteint un autre endpoint de l'API Tiingo **avec ton jeton**.
La portée est limitée à `api.tiingo.com`, donc ce n'est pas un SSRF généralisé — mais c'est
une incohérence gratuite dans un fichier qui a précisément été durci pour ça.

**Correctif :** appliquer le même validateur, par exemple en extrayant la regex dans une
fonction partagée et en ajoutant un `field_validator('benchmark_ticker')`.

## 🟠 7. Pas de `.dockerignore` : la clé API part dans l'image

**Fichier :** [`Dockerfile:16`](Dockerfile#L16)

```dockerfile
COPY backend/ ./backend/
```

Sans `.dockerignore`, cette ligne copie **tout** `backend/`, dont `backend/.env` s'il existe
localement (et `backend/__cache__/`, 1,3 Mo de pickles). Si l'image est un jour poussée sur
un registre, la clé Tiingo part avec — `docker history` suffit à la retrouver, même si un
`RUN rm` la supprimait ensuite d'une couche ultérieure.

Deux points annexes sur le même fichier :
- le conteneur tourne **en root** (aucun `USER`), ce qui aggrave le point 🔴 1 ;
- `COPY frontend/ ./` dans l'étage builder copie `node_modules` s'il est présent (build lent,
  et risque d'écraser les binaires natifs de l'image Alpine).

**Correctif :** ajouter un `.dockerignore` :

```
**/.env*
**/__pycache__/
backend/__cache__/
frontend/node_modules/
frontend/dist/
.git/
*.md
```

et un `RUN adduser --disabled-password app && USER app` avant le `CMD`.

## 🟠 8. Toute erreur de validation 422 fait planter l'interface

**Fichiers :** [`Sidebar.tsx:370`](frontend/src/components/Sidebar.tsx#L370),
[`useOptimization.ts:127`](frontend/src/hooks/useOptimization.ts#L127),
[`Sidebar.tsx:577`](frontend/src/components/Sidebar.tsx#L577)

FastAPI renvoie les erreurs de validation avec un `detail` qui est **une liste d'objets** :

```json
{"detail":[{"type":"greater_than_equal","loc":["body","training_window"],
            "msg":"Input should be greater than or equal to 60","input":20}]}
```

(vérifié via `TestClient` pendant l'audit)

`useOptimization` fait `setError(error?.response?.data?.detail)` — donc `error` devient un
**tableau d'objets** — puis `Sidebar` rend `<Alert severity="error">{error}</Alert>` →
React lève *« Objects are not valid as a React child »*. Pas de message, pas de récupération.

Et les bornes du formulaire ne correspondent pas au schéma, donc c'est facile à déclencher :

| Champ | Borne du formulaire | Borne du schéma | Déclenchable ? |
|---|---|---|---|
| Training Window (custom) | `min: 20` | `ge=60` | oui, 20-59 |
| Rebalancing (custom) | `min: 1` | `ge=5` | oui, 1-4 |
| Max % | `min: 0` | `ge=0.1` | oui, 0-9 |
| Nombre de tickers | illimité | `max_length=30` | oui, 31+ |
| Format de ticker | aucun | `[A-Z0-9.\-]{1,12}` | oui, `BRK B` |

Un champ vidé donne `Number("") === 0` → 422 → crash.

**Correctif (deux temps) :**
1. Normaliser le message côté client — si `detail` n'est pas une chaîne, le mettre à plat :
   `Array.isArray(d) ? d.map(e => e.msg).join(' · ') : String(d)`.
2. Aligner les bornes du formulaire sur le schéma Pydantic (qui reste la source de vérité).

## 🟠 9. Le Rebalancer garde les montants des tickers précédents

**Fichier :** [`RebalancerCard.tsx:42-44`](frontend/src/components/RebalancerCard.tsx#L42)

```ts
const [holdings, setHoldings] = useState<Record<string, number>>(() =>
    Object.fromEntries(tickers.map(t => [t, 0]))     // initialiseur paresseux : une seule fois
);
```

Le composant n'est pas remonté quand `results` change (même position dans l'arbre, pas de
`key`). Après une seconde comparaison sur un univers différent, `holdings` conserve les
anciennes clés, mais `currentTotal` (ligne 52) somme **toutes** les valeurs — y compris celles
de tickers qui ne sont plus affichés.

**Scénario :** tu tournes `SPY QQQ GLD`, tu saisis 10 000 $ chacun. Tu relances avec
`SPY TLT GLD`. L'écran montre SPY = 10 000, TLT = vide, GLD = 10 000 — mais le total affiché
est **30 000 $**, et tous les montants cibles sont calculés sur 30 000. Les ordres d'achat/vente
proposés sont faux, dans le seul composant qui produit des ordres.

**Correctif :** synchroniser sur la liste de tickers.

```ts
useEffect(() => {
    setHoldings(prev => Object.fromEntries(tickers.map(t => [t, prev[t] ?? 0])));
}, [tickers]);
```

(ou plus simplement `key={tickers.join(',')}` sur `<RebalancerCard>` dans `Dashboard.tsx`, ce
qui remonte le composant et remet tout à zéro — plus sûr, moins pratique.)

## 🟡 10. Le drapeau `is_cash` ne se déclenche jamais — et la doc promet du 100 % cash

**Fichiers :** [`backtester.py:441`](backend/backtester.py#L441),
[`config.py:37`](backend/config.py#L37), [`DOCUMENTATION.md:222`](DOCUMENTATION.md#L222)

Le go-to-cash du MVO met tous les poids à 0, **puis** le lissage de turnover (`α = 0,25`)
rebranche 25 % des poids précédents. Il faut donc 5 signaux risk-off consécutifs — environ
**15 mois** au rythme trimestriel — pour descendre sous le seuil `sum(weights) < 0,001` qui
lève `is_cash`.

**Mesuré (MVO, 77 rebalancements) :**

```
périodes marquées is_cash          : 0 / 77
périodes investies à moins de 50 % : 11
poids investi minimum atteint      : 0,40 %   (2022-11-02, après 4 signaux d'affilée)
Sharpes réalisés collés au plafond ±5 : 3 / 77
```

Trois conséquences :

1. **Le filtre `is_cash` de `routes.py:199` n'exclut rien.** Les périodes dégénérées
   entrent quand même dans le rank-IC et dans `edge_statistics`. Le 2022-11-02 (0,40 %
   investi) contribue un couple `predicted = −5,00 / realized = +5,00` — deux valeurs
   plafonnées, donc du pur artefact : un portefeuille à 99,6 % cash a une volatilité quasi
   nulle, d'où un « Sharpe » qui explose.
2. **L'impact chiffré est faible pour l'instant** — en excluant vraiment les périodes à
   moins de 50 % investi, ρ passe de `−0,001` (p = 0,993) à `−0,055` (p = 0,660). Les deux
   sont nuls, parce que le plafond de détectabilité est nul de toute façon. Mais les mêmes
   points polluent aussi le t-stat de `edge_statistics`, qui lui est lu comme un vrai test.
3. **`DOCUMENTATION.md:222` dit « les poids retournent à 0 → le backtester alloue 100 % au
   cash ».** C'est vrai de l'optimiseur, faux du backtest : le lissage le rend impossible en
   un pas. La ligne mérite une phrase de nuance.

**Correctif suggéré :** remplacer le seuil binaire par un seuil d'exposition
(`sum(weights) < 0.5` → `is_cash = True`, ou mieux : exporter `invested_weight` par période
et laisser le consommateur trancher). Et documenter l'interaction lissage × go-to-cash.

## 🟡 Autres points de fond

### 11. Les messages d'erreur utiles sont avalés

**Fichiers :** [`backtester.py:211`](backend/backtester.py#L211),
[`routes.py:240`](backend/app/api/routes.py#L240)

`walk_forward_backtest` lève une `HTTPException(400, "Not enough data. Need at least N
points.")`. Elle est attrapée par le `except Exception` de `_run_strategy` (ligne 240), qui
renvoie `None`. Les trois méthodes échouant de la même façon, `routes.py:362` lève
`ValueError("Could not generate results for any method")` — et c'est ce message générique
que tu vois. Le diagnostic actionnable (« il te faut N jours de plus ») est perdu.

**Correctif :** ré-émettre les `HTTPException` dans `_run_strategy` avant le `except Exception`
générique, et les remonter au niveau du job.

### 12. Le benchmark équipondéré démarre un jour avant les stratégies

**Fichier :** [`backtester.py:540-541`](backend/backtester.py#L540)

`returns.iloc[start_offset:]` inclut le rendement `close(TW-1) → close(TW)`, alors que les
stratégies ne commencent à courir qu'à l'Open de `TW+1`.

```
benchmark : premier point 2007-05-01, 4 815 clôtures
stratégie : premier point 2007-05-02, 4 814 clôtures
```

L'effet est négligeable sur 20 ans (un jour sur 4 814, et le coût initial se neutralise dans
le ratio `dernier / premier`), et les tests de significativité alignent correctement les
index via `dropna()`. Je le signale par exhaustivité, pas parce que ça change une décision.

### 13. Le nuage Monte-Carlo n'est pas déterministe

**Fichier :** [`optimization.py:387`](backend/optimization.py#L387)

`np.random.random(...)` sans graine, sur l'état global de NumPy partagé entre threads. La
fonction est `@memory.cache`, donc le résultat est stable *tant que le cache tient* — après
un vidage, le même run redessine un nuage différent. C'est en contradiction avec le principe
posé pour le bootstrap (`BOOTSTRAP_SEED`, `config.py:53`, « identical inputs must give
identical CIs »).

**Correctif :** `rng = np.random.default_rng(BOOTSTRAP_SEED)` local à la fonction.

### 14. Le rate limit se contourne avec un en-tête

**Fichier :** [`main.py:53-58`](backend/main.py#L53)

`_client_ip` fait confiance à `X-Forwarded-For` sans condition. Derrière Render c'est correct
(le proxy le réécrit), mais si l'app est jamais joignable en direct, `X-Forwarded-For:
<aléatoire>` donne un compteur neuf à chaque requête. Comme chaque job lance 3 threads de
calcul convexe pendant ~30-60 s, c'est le seul garde-fou entre un inconnu et ton quota Tiingo
+ ton CPU.

**Correctif :** ne lire `X-Forwarded-For` que si `TRUST_PROXY=1` est présent dans
l'environnement (à mettre sur Render, pas en local).

### 15. Le cache joblib ne s'évacue jamais

**Fichier :** [`data_provider.py:45`](backend/data_provider.py#L45)

`Memory(CACHE_DIR)` sans `bytes_limit`. Chaque combinaison (tickers, `end_date`) crée une
entrée, et `end_date` vaut la date du jour dès que le champ est vide — donc **une entrée
complète par univers et par jour d'utilisation**. Même chose pour
`calculate_efficient_frontier`, qui hash un DataFrame de 5 000 × 6 à chaque appel (14 entrées
déjà présentes). 1,3 Mo aujourd'hui, mais la croissance est monotone.

**Correctif :** `Memory(CACHE_DIR, bytes_limit="500M")` + un `memory.reduce_size()` au
démarrage.

## 🟢 Ce qui est réellement solide (vérifié, pas survolé)

- **Le moteur walk-forward.** Décision sur les clôtures ≤ T, exécution à l'Open(T+1),
  valorisation aux clôtures. Le bloc de détention va de `T+1` **jusqu'à la date de décision
  suivante incluse** (`backtester.py:396-398`) : pas de trou, pas de doublon, et les intérêts
  du cash sont accrus exactement une fois par jour. La garde `current_idx + 1 >= len(dates)`
  évite proprement le look-ahead du dernier jour.
- **L'alignement du `realized_edge`** (`routes.py:187-189`). Le `.iloc[1:]` sur le bloc
  benchmark n'est pas cosmétique : sans lui les deux Sharpe ne couvriraient pas les mêmes
  jours. Le commentaire explique pourquoi. C'est du travail soigné.
- **La suite de significativité.** Mêmes blocs de bootstrap pour les deux séries (la
  corrélation survit), PBO vectorisé par statistiques exhaustives par bloc (12 870
  combinaisons sans boucle), DSR avec sa correction de queue *reportée* — donc vérifiable.
  Testée dans les deux sens (détecter un effet **et** refuser d'en détecter un absent).
- **L'intersection des calendriers** (`data_provider.py:436`) plutôt qu'un forward-fill sur
  l'union. Le commentaire explique la dilution des corrélations que ça évite.
- **Cohérence Ledoit-Wolf** entre l'optimiseur MVO et les contributions au risque finales
  (`backtester.py:495`).
- **Les secrets ne sont pas dans git.** `.env` et `backend/.env` sont ignorés, aucun fichier
  d'environnement suivi, `__cache__/` exclu. Le masquage de la clé FRED dans les logs
  d'erreur (`data_provider.py:279`) est un détail que presque personne ne pense à faire.
- **39 tests hors-ligne, verts**, CI sur chaque PR (backend + type-check frontend).
